## Findings

### Critical

1. **Потенциальная уязвимость SQL‑инъекции в миграции**
   - **Файл**: `src/Migrations/Monolith/Version20260325143000.php`
   - **Описание**: Миграция использует сырые SQL‑строки без экранирования идентификаторов (таблицы и столбца). Это может вызвать ошибки на СУБД или при совпадении имён с зарезервированными словами.
   - **Рекомендация**: Использовать кавычки для имён или DBAL‑методы.

2. **Удаление валидации в SecurityController**
   - **Файл**: `src/Controller/Api/Dashboard/User/SecurityController.php`
   - **Описание**: Удалена проверка `'if (null === $userDomain->getSelfLabel())'` и добавлено ограничение только через host constraint. Это может создать уязвимость, если host constraint не срабатывает корректно.
   - **Рекомендация**: Сохранить явную проверку статуса лейбла или задокументировать почему она больше не нужна.

3. **Отсутствие транзакции при изменении состояния WhiteLabel**
   - **Файл**: `src/Command/WhiteLabel/BlockWhiteLabelCommand.php`
   - **Описание**: Команда изменяет сущность и сбрасывает кэш без использования транзакции базы данных. При исключении после flush возможен несогласованный статус между данными и кэшем.
   - **Рекомендация**: Добавить транзакцию БД вокруг изменения сущности и инвалидации кэша.

### Medium

4. **Изменение логики регистрации пользователя в SecurityController**
   - **Файл**: `src/Controller/Api/Dashboard/User/SecurityController.php`
   - **Описание**: Удалена проверка наличия selfLabel у UserDomain для маршрута регистрации. Теперь регистрация разрешена только на хосте DashboardDomain, без учёта статуса WhiteLabel.
   - **Рекомендация**: Явно документировать изменение и проверить, не допускает ли оно регистрацию в заблокированных white‑label доменах.

### Low

5. **Нарушена консистентность оформления нового enum‑файла**
   - **Файл**: `src/Enum/WhiteLabel/WhiteLabelStatusEnum.php`
   - **Описание**: В новом файле отсутствует директива `strict_types`, тогда как в большинстве новых файлов PR она включена.
   - **Рекомендация**: Добавить `declare(strict_types=1);` для единообразия.

6. **Операция блокировки не защищена от частичных сбоев после сохранения**
   - **Файл**: `src/Command/WhiteLabel/BlockWhiteLabelCommand.php`
   - **Описание**: Сначала сохраняется статус в БД, затем последовательно инвалидируются кэши. При исключении на этапе инвалидирования статус уже изменён, а часть кэшей осталась неочищенной.
   - **Рекомендация**: Рассмотреть более устойчивую стратегию обработки ошибок вокруг кэш‑инвалидации, возможно, использовать транзакцию.

### Info

7. **Проверка корректности маршрутизации по хосту**
   - **Файл**: `src/Controller/Api/Dashboard/User/SecurityController.php`
   - **Описание**: Изменена маршрутизация с проверки наличия selfLabel на использование хоста DashboardDomain. Нужно убедиться, что это не нарушает логику доступа к маршруту `/api/security/register`.
   - **Рекомендация**: Протестировать сценарии доступа для разных типов доменов.

8. **Валидация ID в команде**
   - **Файл**: `src/Command/WhiteLabel/BlockWhiteLabelCommand.php`
   - **Описание**: Валидация `whiteLabelId` использует `<= 0`, что корректно, но для большей строгости можно проверить `=== 0`, так как ID не может быть отрицательным.
   - **Рекомендация**: Уточнить валидацию на `=== 0` для явного соответствия правила ID.

## Assumptions / Open Questions

Также отсутствуют тесты для новой функциональности. Требуются обязательные исправления перед мержем.
